## 📋 常见项目架构模式参考

### 1. 模块化设计原则参考

#### 常见目录结构模式

**Python 项目常见结构**：
```
project_name/
├── src/ or app/           # 源代码目录
├── tests/                 # 测试代码
├── docs/                  # 文档
├── config/                # 配置文件
├── scripts/               # 脚本文件
├── requirements.txt       # 依赖列表
└── README.md              # 项目说明
```

**Web 前端项目常见结构**：
```
frontend_project/
├── public/                # 静态资源
├── src/
│   ├── components/        # 组件
│   ├── views/             # 页面
│   ├── assets/            # 资源文件
│   └── utils/             # 工具函数
├── package.json           # 依赖配置
└── README.md              # 项目说明
```

**后端 API 项目常见结构**：
```
backend_project/
├── app/
│   ├── models/            # 数据模型
│   ├── controllers/       # 控制器
│   ├── routes/            # 路由定义
│   └── middleware/        # 中间件
├── config/                # 配置
├── tests/                 # 测试
└── main.py                # 入口文件
```

#### 模块划分经验

1. **单一职责**：每个模块专注一个功能领域
2. **低耦合**：模块间通过清晰接口交互
3. **高内聚**：相关功能放在同一模块内
4. **可测试性**：模块设计便于单元测试
5. **扩展性**：考虑未来功能扩展需求

### 2. 代码质量参考标准

#### Python 代码建议

**推荐做法**：
- ✅ 完整的类型注解（Type Hints）
- ✅ 清晰的文档字符串（Docstrings）
- ✅ 适当的异常处理
- ✅ 输入参数验证
- ✅ 有意义的变量和函数命名

**避免行为**：
- ❌ 生成只有几行的极简类或函数
- ❌ 使用 "TODO"、"pass" 等占位符代替实际实现
- ❌ 缺少必要的注释和文档字符串

### 3. 项目验证流程参考

#### 验证步骤（建议执行）

**第 1 步：生成代码文件**
- 使用 `files_controler` 的 `write_file` 工具
- 确保所有模块文件都已创建

**第 2 步：验证代码质量**
- 使用 `shell_controler` 的 `validate_multiple_python_files` 工具
- 验证代码语法和基本质量

**第 3 步：判断是否需要运行代码**

**通常需要运行的情况**：
- ✅ 用户明确要求查看程序运行结果
- ✅ 需要获取具体的输出数据或计算结果
- ✅ 需要验证业务逻辑是否正确
- ✅ 需要测试数据库操作、网络请求等运行时行为

**通常不需要运行的情况**：
- ❌ 仅验证代码能否被 Python 解析
- ❌ 检查是否有语法错误（已由验证工具完成）
- ❌ 确认导入语句是否正确

### 4. 典型场景经验参考

#### 场景 A：创建简单工具（通常无需运行）

**用户需求**："创建一个数据处理工具"

## 🔧 项目修改经验参考

### 1. 增量修改原则

**核心思想**：只修改必要的部分，保持其他模块不变

**操作步骤**：
1. **读取现有代码**：使用 `read_file` 了解当前实现
2. **定位修改点**：确定需要修改的具体位置
3. **最小化修改**：只改动必要的代码行
4. **重新验证**：修改后重新验证质量

---

### 2. 常见修改场景参考

#### 场景 A：添加新功能

**示例**：在用户系统中添加"删除用户"功能

**参考步骤**：
1. 读取 `user_service.py` 了解现有方法
2. 在适当位置添加 `delete_user` 方法
3. 添加对应的测试用例
4. 重新验证质量

**注意**：
- ✅ 保持原有方法不变
- ✅ 遵循现有代码风格

---

#### 场景 B：修复 Bug

**示例**：修复邮箱验证逻辑错误

**参考步骤**：
1. 读取相关文件定位问题
2. 分析错误原因
3. 修正代码逻辑
4. 重新验证质量
5. 运行测试确认修复

**注意**：
- ✅ 先诊断再修改
- ✅ 保留原有功能的完整性

---

### 3. 修改时的注意事项参考

#### ❌ 避免行为
- 直接覆盖整个文件而不了解原有逻辑
- 删除重要功能而没有替代方案
- 修改后不重新验证质量

#### ✅ 推荐做法
- 先读取再修改，了解上下文
- 保持代码风格一致
- 修改后添加注释说明变更原因

### JavaScript 编写参考

#### JavaScript 最佳实践参考

**推荐包含**：
- ✅ 使用 ES6+ 语法（const/let、箭头函数、模板字符串等）

- ✅ 异步操作使用 async/await

## 🛠️ 后端开发架构参考

### 项目架构模式参考

#### 常见目录结构（Flask/Django 示例）

```
backend_project/
├── app/                    # 应用主目录
│   ├── models/            # 数据模型层
│   ├── routes/ or api/    # 路由层（API 端点）
│   ├── services/          # 业务逻辑层
│   └── utils/             # 工具函数
├── config/                 # 配置文件
├── tests/                  # 测试目录
└── run.py                 # 启动脚本
```

#### 常见分层架构参考

1. **Models（数据模型层）**：
   - 负责数据库表结构定义
   - 包含字段验证和数据关系

2. **Services（业务逻辑层）**：
   - 封装复杂的业务规则
   - 协调多个 Model 的操作
   - 处理事务和异常

3. **Routes/API（路由层）**：
   - 定义 API 端点
   - 接收请求参数并验证
   - 调用 Service 层处理业务
   - 返回标准化响应

4. **Utils（工具层）**：
   - 通用工具函数
   - 数据验证器
   - 辅助方法

---

### API 设计参考规范

#### RESTful API 参考标准

**URL 命名参考**：
- 使用名词复数形式：`/api/users`、`/api/products`
- 资源嵌套不超过两层：`/api/users/{id}/orders`

**HTTP 方法映射参考**：
- `GET`：查询资源
- `POST`：创建资源
- `PUT`：全量更新资源
- `PATCH`：部分更新资源
- `DELETE`：删除资源

**状态码规范参考**：
- `200 OK`：成功返回数据
- `201 Created`：资源创建成功
- `400 Bad Request`：请求参数错误
- `401 Unauthorized`：未认证
- `404 Not Found`：资源不存在
- `500 Internal Server Error`：服务器内部错误

## 🔗 相关技能

- **files_controler**：用于创建和管理项目文件

  - 核心方法: `write_file`(写文件), `read_file_full`(读完整文件), `replace_content`(替换内容), `read_file_lines`(读指定行), `list_directory`(列出目录), `get_file_structure`(获取文件结构), `find_method`(查找方法), `locate_file`(定位文件), `replace_lines`(替换行), `get_file_info`(获取文件信息), `delete_lines`(删除行)
